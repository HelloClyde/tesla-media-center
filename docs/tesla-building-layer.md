# Tesla 混合地图：App 立体建筑

2026-09-28：接入 App 原生 BMD 建筑瓦片，未使用 Web SDK 或 Web Key。

## 已验证的链路

`/ws/render/bmd/version/` → tileType 5、源级别 15 → BMD 8000 目录 → 第 50 节轮廓和建筑分部 → Python 经纬度/高度 DTO → Tesla Three.js 场景。
第 51 节提供建筑样式类别及子类，已关联 App 昼夜样式表；本版只采用颜色一致的纯色材质，未知贴图与多面材质仍使用中性色。旧 type 3 多数据格式不属于本次链路。

固定版本 libamapr.so 的 ReadShape 0x15a5f3c、ReadFeature 0x15a63ec、ParseBuilding 0x15a66a8 用于核对格式。轮廓使用位压缩坐标及累计有符号偏移；部件带轮廓引用、平移、基底高度、部件高度。32 位变长数最多读取五字节，不能替换为通用 64 位 varint。地理展开与原生 0x14ae678/0x14ae6d8 对应，保留源数据米制高度。

## 展示与容错

建筑、道路、车辆共享坐标、相机及深度。部件按 base/height 挤出，合并绘制并限制顶点数。镜头至车辆之间的遮挡楼体局部镂空，避免遮住车辆；默认混合视角拉远以展示街区。近景瓦片接入已有磁盘缓存与压缩响应。建筑失败时保留道路并提供重试；切页取消请求并释放几何、材质和纹理。

已用真实建筑和道路解码结果做浏览器回放，检查模型显示、缓存稳定、模式切换与建筑 502 降级。浏览器回放的车辆位置与接口响应为测试夹具，不代表已完成实车验收。

## 明确边界

本版支持已验证的单轮廓、平移部件和原始分段高度，不是手机 App 的完整精细建筑渲染器。非单位缩放、非零旋转及未知部件类型明确计为缺失，不猜测变换；复杂孔洞语义、原生纹理和精细地标仍需单独验证。无建筑覆盖的区域显示“此处暂无建筑数据”。实车 GPU 性能仍需验证。

测试包括截断/越界拒绝、负数 varint、轮廓偏移、瓦片接缝、挤出高度与方向、去重、缓存级别隔离，以及生产构建。

## IndexModel 索引结构与位置计算

新增离线诊断工具 `tools/amap-app/model_index.py`，未挂载到生产接口。解码入口由日志交叉引用定位：`0xc7398c → 0xc73b30 → 0x1ada34c`，根字段描述表在 `0x1b335b8`。14 个嵌套消息的字段号、类型、必选/可选/重复属性已逐项与原生描述表核对。尚无非空在线索引样本，因此报告始终标记 `verifiedLiveIndex=false`、`georeferenced=false`，不能把合成测试当作联网成功。

已确定的关联结构：根字段 3 为重复分区；分区字段 7 为模型定义，字段 6 为实例分组。模型定义字段 1 与实例字段 1 使用同一个 64 位 ID 关联；模型字段 2 包含字符串引用和可选整数，字符串是否为完整 URL、相对路径或别名需用真实样本及后续请求代码验证。工具保留未知语义的字段号，64 位值转十进制字符串避免前端精度丢失；缺失定义的实例明确报告 unresolved，不创建替代模型，也不自动访问任何字符串地址。

位置运算链路已单独验证：`0xc740b8 → 0x1446ab4 → 0x1446a34 / 0x1446b80`。实例第二种位置记录使用 63 位交错编码坐标以及两个整数范围值，原生函数解交错、恢复符号、取半宽高，再缩放为角度。新增 `model_index_coordinates.py` 保留原生四个输出槽位及边界行为，不做 GCJ/WGS 转换、不自动排序或套入地图。

使用本机 Unicorn 执行固定版本原生函数 0x1446ab4，与 Python 移植比较 103 组确定性输入，全部在 1e-12 容差内一致；6 组原生输出已固化为无需 APK/Unicorn 的回归测试。这个结果证明计算移植一致，不证明地标实际位置、朝向、坐标基准或显示效果正确。

请求映射的静态证据：工厂 `0x15aa62c` 创建 IndexModelSource 并设置源类型 40/41；`0x14490f8` 将其转换为内部枚举 20/19；反向 HTTP 类型表 `0x166e59c` 对应 16/15。源控制器使用 `0x14b2ef8`，索引处理后经 `0x14b34ec` 关联数据。仍须追踪控制器如何产生实际请求 ID，不能把实例的交错坐标编码直接当作请求 tileId。

本轮有界请求：CCTV 与外滩附近源级别 16 的类型 15/16 均为空；类型 15 的 ID=0 假设也返回空 payload（响应省略默认值 0 的 ID 字段）。没有继续扩展猜测范围，也未放宽生产下载器的身份校验。旧类型 4、内部渲染类别 75/76、源类型 40/41 与 HTTP 类型是不同层的编号，不能互换。

验证：`python -m unittest discover -s tools/amap-app -p 'test_model_index*.py'`，9 项通过，覆盖原生坐标参考、64 位关联、未解析引用、重复定义、错误线类型、缺失字段、截断、非有限数与字符串限制。未知索引字段跳过，已知字段严格检查；解码只用于调查，不作为已上线地标能力。

### 类型 22 分块与完整性校验

新增 `lane_render_blocks.py`，由 `lane_render.py` 自动调用并导出独立块。原生 `16693d0 → 16728ec` 使用描述表 `1b9c460`，根字段 1 为 uint64 tileId，字段 2 为 repeated message；子表 `4e4448` 的字段 1/2 为 uint32，字段 3 为 bytes。`166a240` 将 bytes 交给数据提供器，`1669304` 将字段 1 写入 u16 块编号。字段 2 在两份实网样本中均未出现，暂保留原名。

校验链路 `160766c → 1604bac / 1b1f9a0(crc32)`：前四字节按 little-endian 读取，与剩余字节的 CRC32 比较。北京块 ID=1、74,258 字节、CRC `89a33b33`；上海块 ID=3、588,311 字节、CRC `a40ea4f4`，均通过校验。损坏数据、重复块编号、无法装入 u16 的编号、错误 wire type、超过 64 块和身份不符均拒绝。相关测试现为 18 项通过，两份已下载样本也通过新的提取器，报告分别保存在本地 `lane-blocks-beijing` / `lane-blocks-shanghai`。

**尚未完成**：块内不是普通 BMD 8000 格式，也不是直接可绘制的坐标数组。原生 `1639334` 会为缓存重新封装版本和块目录；不能把这个内存/缓存结构当作服务器原始格式。当前两份响应仅有主数据字段 5，尚未取得额外数据块。真正边界使用链路已追到 `12d2274 → 1350a28/105b434 → 105b4c4 → 104aa44/104b624`，其读取的是数据提供器处理后的对象，尚需连接到原始二进制块解析。没有输出猜测坐标、车道数或高程，也未改变前端场景。

### 解析后边界点读取器与原生对照

新增离线 `lane_boundary_points.py`，输入必须是**已解析的 FlatBuffers 边界表及其位置**，不能输入 LNDS 下载块。原生 `104b5e4/104b5ec` 通过表首有符号偏移找到 vtable，读取槽位 0（vtable +4）指向的向量；`104aa44` 返回点数，`104b624` 按 24 字节步长读取三个 double。Python 读取器检查表、向量、点数、缓冲区范围和有限数，保留三个原始数值，不命名坐标系或高程单位。

本机 Unicorn 执行固定版本 `104b624`，33 份合成表、459 次读取（包括末端越界时的原生零值）与 Python 结果逐值相同；验证脚本保存在 `.local-data/amap-app/verify-boundary-accessor.py`。这是访问器一致性验证，**不是从真实下载块解出了 459 个点**。新增 5 项测试后，`test_lane*.py` 共 23 项通过。

进一步排除了一条错误路径：`DataProviderFactory` 的 `15f1678 → 15fe844` 建立 vtable `1b99f90`；其 +0xb0 方法 `15ff738 → 164b8d8` 创建块数组，块的赋值函数 `164bb8c` 只是保存原始数据及长度，并未转换为上述边界表。因此不能把赋值成功视作几何解析成功。剩余关键连接仍是原始 LNDS 二进制到 FlatBuffers 几何对象，前端车道显示尚未上线。


### 核心转换追踪记录（尚未突破）

本轮只追踪原始块的消费者，没有增加外围解析器或把合成数据当作实网几何。确认车道引擎加载 `10326b4` 将 LaneAdapterParam +0x18 的数据提供器传给内部引擎；`1070b28` 调用 IDataProvider vtable +0x138。该方法 `15ffc34` 返回对象 +0x158；当 DataSource=2 时，`15ff0ec → 16728f8/1672938` 创建此 LNDS 提供器（vtable `1b9c4d0`）。

引擎自身的构造路径 `10320bc → 10716e4` 创建 vtable `1b70840`；加载方法 `107173c` 创建 `1079cdc` 数据上下文，通过 `107661c` 保存上述提供器，`107664c` 取回。`10768a4 → 119cee8` 将提供器传入另一个按类型注册处理器的对象；此处尚未证明哪一个注册项完成原始二进制到 FlatBuffers 的转换，不将其命名为已确认的解码器。

### 原始块到真实边界坐标已离线打通（2026-09-28）

本节更新上文“尚未突破”的历史状态。北京、上海真实 type-22 下载块已通过原生解析及几何转换，输出真实边界点。**尚未接入 TMC 页面，坐标系、高度单位和线型语义仍需核验。**

固定版本 17.00.0.2005 的确认链路：

1. `119f470 → 124b630 / 1249820`；读取器 `1248f28` 调用 IDataProvider +0x168，即 `15fff3c` 返回 +0x180 的 GuideLndsDBManager，而非此前追踪的 +0x138 下载提供器。
2. `1253c14 → 12479a8 / 12479cc` 调用该管理器 +0x60；结果经 `1247ce0 → 1247f28 → 1223da4` 遍历实际块。
3. `1223f80 → 1ac94e8` 是原始块解析入口。输入为 `{pointer, uint32 length, int32 flags, alloc callback, free callback}`，本次 flags=-1。原生解析器跳过前 8 字节，经 `1ac96cc` 等函数解析。两份真实块都返回 0，产生非空的 0x210 字节对象。
4. 按调用方写入块编号（对象 +0）和 LNDS uint32 编号（+4，由 `160d0e4` 从渲染 ID 转换）。`1223f1c` 初始化构建器，`1225638` 几何转换返回 1，`1225cdc` 完成 FlatBuffer。输出指针为 context +0x88，长度为 `u32(+0x78) + ptr(+0x80) - ptr(+0x88)`。
