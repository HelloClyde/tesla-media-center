# 杭州地图体积与首屏加载调查（2026-09-30）

## APK 内的离线地图

固定版高德 17.00.0.2005 APK 的 `assets/common/OfflineDbV6.db` 中，
`allcity` 表的杭州（adcode 330100）记录 `mapZipSize=46,458,634` 字节
（44.31 MiB），`routeZipSize=42,959,027` 字节（40.97 MiB）。
这是 APK 自带的离线包**目录元数据**，并非 APK 内已下载的杭州地图；
`citydata` 下载状态表为空，杭州记录的 `mapZipName` 也为空。
因此不能把这两个数字当作当前版本实际下载后的占用量。

高德 Android 3D 地图 SDK 的[离线地图说明](https://lbs.amap.com/api/android-sdk/guide/create-map/offline-map/?type=spa)
指出，本地有离线地图数据时会优先加载，并提供按城市下载接口。
此 APK 的 `libamapr.so` 还包含 `save2DBForBmdTile`、
`saveOnlineDataInner` 等在线瓦片写入本地数据库的函数标识；
这些静态证据支持 App 有离线包和在线瓦片缓存两套机制，
但不能确定一台特定手机当前实际缓存了多少。

## 当前 TMC 地图的体积

TMC 并未读取上述离线城市包。它请求高德 BMD 瓦片，服务端解码成 JSON，
以 zlib 压缩后保存在 SQLite，并以 gzip 向车机浏览器传输。
默认缓存上限 512 MiB、有效期 7 天，所有车机共用服务器缓存。

杭州政府[地理位置资料](https://eng.hangzhou.gov.cn/art/2024/7/22/art_811223_58876367.html)
给出的经纬度外接框为 118°20′–120°37′E、29°11′–30°34′N。
按 TMC 的地理网格计算，整块外接框在 level 14 有 13,335 块，
另有 level 3/6/8/10/12 共 936 块。外接框包含市界之外的区域。

从固定 APK 的在线 BMD 接口抽测 25 个均匀分布的 level 14 网格：
TMC 的 SQLite zlib 单块为 0.1–51.2 KiB，均值 9.7 KiB；
杭州市中心另测一块为 198.2 KiB。将 25 块均值机械乘以外接框，
仅 level 14 约为 126 MiB。中心城区的高密度瓦片被均匀抽样低估，
而外接框又包含市外区域；**126 MiB 不是全杭州实测包大小**。
若要得到精确值，需要按市界和需要的缩放级别逐块下载并统计。

中心城一块原始上游 BMD 响应共约 50.6 KiB，解码后的 SQLite 数据
为 198.2 KiB、向浏览器传输的 gzip JSON 为 178.3 KiB。
这里更重要的约束是服务器到车机的网络传输量和弱网下的首屏时间。

## 首屏等待点与改进

此前高缩放视野串行等待 3、6、8、10、12、14 级源数据，
每级都启动地图 helper、获取版本信息、下载最多三层瓦片、解码并返回。
杭州中心样本的单级 helper 约 2–3 秒，level 10 的一个网格就包含
9,452 条道路，解码 JSON 为 3.68 MB。车机端还需创建和绘制这些要素。

本次将请求顺序改为：3 级概览 → 当前最高精度 → 其余级别从高到低。
绘制顺序仍为从粗到细。这样概览可先出现，街道细节无需等完全部中间级别。

路线预热现已接入：选定路线后，前端按当前进度取前方最多 8 公里的
level 14 中心瓦片和邻接瓦片，总数最多 32 块；每次最多请求 2 块。
只有当前视野加载完成后才调用登录保护的
`POST /api/amap-app/map/bmd/prefetch`。服务端沿用地图 helper 和 SQLite 缓存，
只向浏览器返回持久化状态，不传输展开的几何 JSON。
路线进度每前进约 2 公里更新预热范围；路线切换或页面停用后不继续排队。
原 JSON 接口的本机测试中，杭州中心一块预热用时约 2.47 秒，返回体
69 字节；随后地图请求命中磁盘缓存，用时约 0.10 秒（未压缩 JSON
约 0.94 MB）。BMD 预热沿用同样的缓存命中机制。
这些是本机样本，不代表车机网络和绘制耗时。

## 车机侧 BMD 几何解码

地图视野现在请求 `POST /api/amap-app/map/bmd`。服务端只解开上游 BMD
的 Zstandard/LZ4 传输压缩，返回有界的 BMD 分段和打包样式；浏览器 Worker
解码道路、面、站点和地名，主线程继续绘制。该接口有独立缓存键，路线预热
也填充同一份缓存。若 Worker 或解码失败，当前页面回退到原 JSON 接口。
15 级建筑仍走原有接口。

## 3D 导航路线预载（2026-10-01）

APK 的静态分析确认在线瓦片与离线包有本地缓存路径，但没有确认其 3D
导航精确的路线预取窗口或调度参数。TMC 因而沿用已验证的路线走廊策略，
针对自己的 3D 渲染器增加预载：前方 2.5 公里内最多 8 块 level 14 道路瓦片、
前方 1.5 公里内最多 12 块 level 15 建筑瓦片。每次只提交一块，
且必须先完成当前 3D 画面加载。
进度每前进约 500 米更新窗口；换路线、切换视野或卸载时取消浏览器侧排队。
切换到 3D 时暂停隐藏的 2D 瓦片加载，以免两套地图争用服务端地图 helper。

3D 继续从 `/api/amap-app/map` 读取已解码数据。最近的每级最多 4 块
提前请求并保存在车机浏览器内存，后续视野可直接读取；其余瓦片调用同缓存键的
`/api/amap-app/map/prefetch`，只返回是否已写入服务器缓存，不传输几何数据。
服务端现允许该接口预载 level 15 建筑，仍限制单批至多两块且不接受
level 15 BMD 原始模式。当前策略是服务端预热，不是完整城市离线包，
也不声称逐项复刻高德 App 的内部调度。近处预载会提前消耗网络流量，
但每级至多 4 块，且可被当前画面加载打断。

同一杭州坐标的实测样本（每次请求一块；gzip 后体积，包含一次样式表）：

| 级别 | BMD 响应 | 原 JSON 响应 | 本机 JS 解码耗时 |
| --- | ---: | ---: | ---: |
| 3 | 35.7 KB | 41.3 KB | 11.5 ms |
| 6 | 84.0 KB | 107.1 KB | 15.2 ms |
| 8 | 59.8 KB | 87.2 KB | 10.7 ms |
| 10 | 230.6 KB | 508.5 KB | 59.4 ms |
| 12 | 98.4 KB | 267.5 KB | 19.5 ms |
| 14 | 61.0 KB | 174.7 KB | 7.9 ms |

六个级别的解码结果与现有 Python 解码器逐要素比对，名称、坐标、
面样式和标签一致。耗时取自本机 Node，同等代码在车机浏览器中的耗时
仍需实车测量；首次样式表只占每批响应一份，多块批量时相对开销更小。

后续最值得验证的改进：

1. 对版本查询与固定样式解析做短期缓存，减少每个级别重复初始化。
2. 测量车机上的网络耗时、BMD 解码和 Canvas 绘制耗时，
   再决定是否合并几何或使用 WebGL 绘制。

## 2026-10-10 导航启动加载优化

- 2D 优先下载当前视图中心的详细道路，再补齐其他源级别；前台单批最多四块，邻域预读单批一块。缩放或移到缺失瓦片时，中断浏览器端后台预读，转入当前视图加载。服务端已运行的 helper 仍会完成并写缓存。
- 初次定位和搜索选点先设置真实视图，再初始化地图层，避免默认世界视图占用加载通道。
- 2D/3D 共用最多八块最近解码瓦片的内存窗口，遵循缓存有效期和清空操作；内存命中先显示，不等待 IndexedDB。重新进入地图页会重新检查磁盘缓存。
- 3D 首帧可直接显示缓存道路；新下载道路也会在建筑响应结束前显示。建筑和地表随后补齐，保留原始图层绘制顺序和 BMD 数据。
- 服务端将同一瓦片的道路、地表和标注改为并行请求，所有瓦片、图层合计最多四个工作线程，保持图层选择、失败标识和缓存完整性规则。

本机用杭州坐标 `(120.29, 30.24)` 对照同一 level-14 瓦片，先预热双方共用的版本目录，按旧、新、新、旧交替执行。旧实现耗时 1.816 / 1.733 秒，新实现 0.734 / 0.731 秒；完整结果的排序 JSON SHA-256 一致，各层无失败。这是单块上游请求对照，包含 helper 初始化和样式解析，不代表车机首屏或整幅地图耗时。车机弱网下的完整首屏仍需实际测试。

## 2026-10-10 地图缩放优化

- 2D 道路使用源要素索引作为稳定标识。缩放改变可见性或样式时复用已有 GeoJSON/Polygon，只在实际颜色、宽度或透明度变化时更新样式；标签 DOM 只在新增或替换标签时创建。道路外描边和内填充分开 Canvas 层，防止新增道路的外描边盖住已有填充。
- 绘制队列每个显示帧最多执行一个批次，预算约 4 ms、最多 256 步；较重的单个几何步骤仍可能超出预算。任何缩放手势（包括车辆跟随模式）都会暂停绘制和新增加载，已发出的前台下载仍写入缓存，缩放结束后补齐当前视野。
- 3D 按钮和滚轮缩放使用约 180 ms 的相机距离过渡，连续输入可以累积、反向和取消，并遵循 OrbitControls 的距离限制。双指缩放继续使用 OrbitControls。
- 3D 手势过程中保留当前道路、建筑网格，继续对齐地理坐标；到达的瓦片暂存，手势停止约 120 ms 后合并显示，避免多次建筑重建插入缩放帧。导航车辆位置继续更新。地标引起的普通建筑裁剪也延后到手势结束。

回归验证覆盖跨缩放级别的几何复用、样式透明度变化、手势中瓦片到达、绘制帧预算、3D 过渡取消与边界、延后呈现和拖动后的坐标对齐。车机上的帧率改善尚未实测。

## 2026-10-10 交互与加载并发优化

之前只暂停了图层绘制，缓存 `JSON.stringify`、读取后的 `JSON.parse`、逐次扫描磁盘缓存完整负载，以及 Worker 大对象交回主线程仍可发生在手势期间。

- 2D 在滚轮、触摸和指针按下的捕获阶段立即暂停重处理，不再等待 Leaflet 延迟触发 `zoomstart`。连续手势共用约 140 ms 的稳定期；双指交互全部结束才恢复。已经开始的前台网络请求保留，后台预读暂停。
- BMD 解码、缓存 JSON 编解码和 gzip 使用同一个复用 Worker。完成后先只发送小通知，收到主线程在交互结束后的许可再交回大对象；因此 Worker 内同步解码也不会抢在排队的暂停消息前提交大结果。刚解码的瓦片通过 Worker 内引用直接做缓存压缩，省去把整块几何从主线程再次复制回 Worker；引用最多保留八块，完成持久化编码后释放。
- IndexedDB 升级为版本 2，沿用原瓦片格式，新增大小、读写时间的复合索引。统计及淘汰使用 `openKeyCursor`，无需取出每块压缩瓦片或 GLB 数据。原缓存继续可读，清空仍会使排队写入失效。
- 2D 按带边缘缓冲的视野裁剪道路和地表；同一源瓦片内平移也会刷新可见图层。道路过滤过程也纳入每帧绘制预算，减少整块瓦片 `flatMap` 的连续主线程开销。
- 3D 同样裁剪地表与道路；没有道路变化时不重画地面，没有建筑变化时不重建建筑。仅补齐建筑或重复呈现已缓存瓦片时，避免连带重建路面、路口覆盖层和车道网格；手势期间到达的车道几何也延后提交。

以实际杭州 `(120.29,30.24)` level-14 BMD（109,210 字节）验证生产构建 Worker：zoom 17 的 397 条候选道路中，约一公里的指定视野保留 207 条；缓存 gzip 为 46,505 字节，JSON 往返 SHA-256 一致，交互期间大结果确实等到许可后才交付。这是本机 Node Worker 的功能与裁剪验证，并非车机浏览器帧率测量。车机 GPU 上传和单个较复杂几何的主线程创建仍可能超过帧预算，实际顺滑度须在设备上验收。

69 项相关回归测试通过，覆盖 Worker 延后交付与原对象缓存编码、旧缓存迁移和元数据淘汰、视野内平移裁剪、双指与滚轮交互、3D 建筑更新不触发道路覆盖层重建、相机与缩放队列；类型检查及生产构建通过。

## 2026-10-10 3D 地面覆盖与首屏呈现

- 缩小后的蓝色区域并不全是等待下载：之前的 3D 地面固定为 600 米见方，远处没有地面网格。保留该精细导航区域，增加 6 公里见方、1024 像素的外围地面，用相同的 APK BMD 地表和道路绘制，覆盖当前相机可见距离。外围只请求 level 12 及以下底图，不扩大 level 14 详细道路、level 15 建筑及车道的下载范围。
- 首批 level 14 只请求中心一块，减少邻块慢响应拖住第一幅道路的情况。外围地图排在建筑下载前，所有级别每到一批即可呈现；此前只有 level 14/15 中途呈现，低级别地表要等全部请求结束。
- 磁盘缓存按相同优先级分批读取和解码；一块缓存道路可以在其余缓存地表和建筑尚未解码完成时显示。内存缓存仍先同步呈现，交互期间仍暂停重建几何。
- 取消固定 280–600 米的场景雾效，避免相机拉远后整幅地图被雾色覆盖。

56 项相关测试通过，覆盖地表在建筑响应阻塞时呈现、精细区域外的道路绘制、磁盘缓存分批显示、原始 BMD 及 Worker 故障恢复、预读、车道、立交高度与相机。网络冷启动及车机实际耗时没有作为该测试结果量化。

## 2026-10-10 3D 拖动后加载永久等待修复

3D 手动平移会同步隐藏 Leaflet 地图的中心，触发 `movestart` / `moveend`。此前停用的 2D 地图仍在开始事件里占用共享交互通道，但结束事件因 `active=false` 直接返回，没有释放通道。后续 BMD 解码、磁盘缓存解码和 3D 瓦片呈现全部等待 `waitForMapIdle()`，因此已下载的部分道路一直显示，状态却永久停在“正在补充建筑与地表”。缩放开始事件也存在同样问题。

- 停用或已销毁的 2D 图层不再响应交互开始事件；切换到 3D 时清理未完成的指针、滚轮定时器和缩放状态，并释放交互通道。
- 首次创建 2D 图层时立即应用当前 2D/3D 状态，避免在 3D 已打开后才取得定位时启动隐藏图层的交互。
- 回归测试先在旧实现复现隐藏地图移动、缩放导致解码永久等待，再验证修复后的恢复，以及在 2D 缩放途中切入 3D、随后切回 2D 仍可加载。

本机杭州 `(120.29,30.24)` 七个源级别的单块缓存 BMD 请求耗时约 24–48 ms；新 helper 冷启动测试的单块 level 14 / 12 / 15 总耗时约 1.58 / 0.96 / 0.60 秒，包含目录查询、图层下载和解析。此抽样用于区分服务端响应与前端永久等待，不代表车机弱网下的整幅地图加载速度。

60 项加载、缓存和交互回归测试通过；类型检查及生产构建通过。本地浏览器实测首次 3D 加载完成为 208 栋建筑，手动拖动、缩放后新区域完成为 151 栋建筑。
