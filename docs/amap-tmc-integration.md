# 高德 App 地图导航接入

2026-09-27：已从旧的道路摘要实验页切换为地图导航。算路仍使用消费者 App 的接口，没有替换成开发者路线 API。

## 使用

访问 `/#/apps/amap`，底图为高德地图瓦片（Leaflet 显示，不需要网页 Key）。初始北京坐标明确标为示例。点击「定位」设置当前位置，选择「终点」后在地图点击选点，也可输入 GCJ-02 经度、纬度并回车。当前不含地址/POI 关键词搜索。

「规划路线」发出真实 App HTTP 请求，显示候选路线；选择方案后「开始导航」使用浏览器实时定位，提供位置跟随、剩余距离、转向提示、中文语音和偏航重算。「模拟导航」使用同一条真实算路结果回放，始终显示模拟标识，不读取车辆定位。

浏览器定位先通过 `coordtransform` 将 WGS-84 转为 GCJ-02。精度超过 60 米不推进引导；连续 3 次偏航且距离超过 40 米/1.5 倍精度时重算，重试间隔至少 20 秒。过期定位不处理，15 秒无新定位提示信号中断。退出或卸载页面会清理定位监听、回放/信号定时器、请求、地图与语音。

## 调用链

`AmapAppView.vue → POST /api/amap-app/route → 隔离 Python 子进程 → /ws/mapapi/navigation/auto/ (route_version=5.1) → 32 字节分帧 → Zstandard → Protobuf → 有界路线 DTO → Leaflet / 浏览器引导`。

原 `/probe` 路径保留兼容，使用同一新版解码器。`/status` 的 configured 仅表示本地资源可用。只有新版解码和几何检查通过才返回 ready/navigationAvailable。

- APK 17.00.0.2005 的 `libamaptbt.so` getRouteVersion JNI 位于 0x4a8bd4，读取 0xcb863 的字符串 `5.1`；旧 Java 构造器的 `2.5.3` 只是默认值。
- `libassembly_kit.so` DrivePathCodecImpl 0x714e0 → 0x7124c / 0x71378 → DrivePBPathDecoder 0xb60c8，提供分帧与解压链证据。
- Protobuf 版本字段 51；逐段坐标为 zigzag 增量，每段首点重新起算，比例 3,600,000 单位/度。逐 link 的坐标索引和数量须完整覆盖所属段。
- 长度、压缩大小、坐标范围、起终点邻近关系、逐段连接差异、坐标覆盖和总距离交叉检查；未知或不一致结构拒绝导航。
- 上游部分路口留有连接间隙。保留分段、记录 breaks，不生成虚假连接线；超过 100 米的间隙拒绝。显示距离按已解码几何计算。转向优先使用已验证的主动作码；辅助动作码 6/7/8 分别提示中间/右侧/左侧岔路，未识别的动作才按相邻路段方位估算。该辅助动作定义也见[北斗 GNSS 标准表 A.5](https://m.beidou.gov.cn/zt/bdbz/202407/W020240718511922218152.pdf)。
- 签名材料仅在子进程内存中使用；固定 HTTPS 主机、禁用重定向、40 秒执行上限、响应 4 MiB 上限、解压 16 MiB 上限。前后端需要 TMC 登录且返回字段白名单过滤。

## 高速服务区提示

App 5.1 驾车路线的部分高速路段在 `segment.5` 内带设施名称；
`segment.5.4` 在实测路线中分别出现服务区和收费站名称。解码器只将
以“服务区”或“停车区”结尾的名称加入对应路段，收费站不算服务区。
杭州至上海、北京至天津、上海至南京三条真实路线分别识别出 3、2、6 个服务区。
导航中显示前方两个服务区，并在进入其标注路段前约 5 公里播报一次；
临近转向时暂缓服务区播报。

此路由响应没有提供服务区入口的精确坐标或充电、加油、厕所等设施清单。
页面显示的距离是该路段中点的估算值，并明确提示驾驶员留意道路标志；
语音不宣称精确入口距离。[高德专业导航 SDK 文档](https://lbs.amap.com/api/harmonyosnext-navi-sdk/guide/navigation-map/navi-info)
描述了可返回类型、名称、经纬度和距离的服务区回调，但当前网页导航
没有运行该 SDK，不能把它的字段等同于此路线响应。

## 验收与限制

- 新版真实 HTTP 样本：北京两组起终点和杭州一组；共 5 条候选路线，52/48/85/140/138 个坐标，全部完成解析与 link 覆盖检查。
- 本机浏览器实际完成：真实请求 → 地图折线 → 模拟车辆跟随 → 路口提示变化 → 到达目的地；检查 773×601 布局。
- 研究工具 52 项、后端 12 项、前端几何 4 项测试；类型检查和生产构建。
- 实时定位/偏航逻辑已接入，但当前机器未做特斯拉 GPS 路测。浏览器权限、定位精度、语音支持取决于车机。
- TMC 不运行 Android APK 进程，无法直接订阅它的事件总线。开始实时导航后，Python 后端使用同一路线会话请求 APK 的二次导航 `routeguide`，从原生 NCP 事件中解出连续限速区间和带速度数组的摄像头，再按路线里程在网页端产生与 `NaviEventTypeSpeedLimitSection`（452）和 `NaviEventTypeShowNaviCameraExt`（95）相同语义的状态变化。452 更新当前限速牌并触发持续超速提醒；95 显示前方固定／区间测速牌和语音。路线未匹配、定位不可信或二次请求失败时保留未知状态，不使用路况速度推定法定限速。车机实测的事件位置与发声仍待核对，其他原生能力也未完整复刻。
- 地图标志：规划路线中的红绿灯坐标在 2D／3D 使用 APK 地图引擎 `icons_10000` 图集提取的原版竖向三色灯，不再使用红色圆点或手绘灯牌；只有可信、未过期的前方实时相位才附加对应灯色的倒计时。原生 `routeguide` 摄像头的路线里程投影到路线几何，2D／3D 地图标志使用 APK `icons_10001` 图集的摄像头剪影和红圈，沿行进方向向右侧偏移 18 米；限速数字仍由导航提示展示，不再挂在地图图标下。事件缺失时不凭空添加测速标志，路侧偏移是当前显示规则，实际车机尺寸和遮挡仍需验收。

底图接口参考：[高德 TileLayer 文档](https://lbs.amap.com/api/maps-javascript-api/reference/layer/tilelayer)；显示层参考：[Leaflet API](https://leafletjs.com/reference.html)。

## 导航限速与测速事件（2026-10-03）

开始实时导航时，后端使用已规划路线会话向高德 App 的二次导航 `routeguide` 接口请求沿途扩展，解码带坐标的限速标志点并映射到路线进度。接近标志时，车机页面显示“前方限速标志”和距离；定位可信且附近没有更紧迫的转向播报时，使用现有导航语音播放提醒。二次请求失败不会阻止导航。

同一二次响应的 kind=3 NCP 数据另带限速区间和测速摄像头。杭州至嘉兴约 80 公里样本中，解出 21 段区间、66 个带速度的摄像头事件，以及上述 kind=2 的 43 个标志点。区间长度与 5.1 原生 link 长度逐段吻合；摄像头坐标和剩余里程也与路线几何相符。三类数据分别用于当前限速／超速提醒、前方测速提醒、前方标志提醒。首次动态导航请求只在开始导航时进行；请求失败不妨碍原有路线导航。车机上实际位置与播报仍需验证。

路况图层开关只影响拥堵线及其两分钟刷新；关闭路况不会清空或停止
限速、测速、限速标志及红绿灯事件。重新打开路况会恢复刷新并立即请求
一次最新状态。实时红绿灯请求只在当前位置与规划路线匹配、定位精度
不超过 25 米且融合引擎处于可信跟踪状态时发送；超过 10 秒没有可信
位置或进入隧道估算／恢复阶段时，页面隐藏实时灯色与绿波建议，避免
继续显示基于旧位置的倒计时。

## 路口放大图

路口放大图由 App 的 `new_vector_cross` 请求取得原始 JPEG 路面层与 PNG 箭头层。进入路口前 700 米开始请求，450 米内展示。原始响应明确缺少图片层时记为该路口无图；后端繁忙、网络错误或异常响应则在同一路口 20 秒后至多重试一次。离开路口、路线切换或页面卸载会取消待执行的重试，避免连续请求。

## 高德 App 路线拥堵（2026-10-03）

路线 5.1 响应中，每条 link 的交通状态直接对应 APK `RouteLink.getLinkTrafficStatus()` 的 `LinkStatus.status`。按 APK 的 `TMC_STATUS` 值，2 是缓行、3 是拥堵、4 是严重拥堵；0 是未知，1／16 是畅通。TMC 按原始 link 坐标范围绘制拥堵段，并在 2D／3D 导航及路线预览中保留相同颜色与进度裁剪。杭州与杭州至嘉兴的保存样本均解出拥堵段，不需要额外的 Web 交通态势 Key 或地图道路匹配。

开始实时导航后，每两分钟用同一高德 App 5.1 算路接口重新请求。只有 link ID 序列、路线坐标和长度都与当前导航路线吻合，才替换路况颜色；若高德改选另一条路线或请求失败，保留上次可靠的结果，待重新规划后再更新。该刷新会重新请求完整路线，目前没有解析 APK 增量 TMC 通道。原 Web 交通态势代理、路况 Key 设置和 45 秒轮询已移除。

## 导航 3D 视图（2026-10-03）

3D 导航采用车后方朝前的透视镜头，显示本项目已有的 Model Y 立体车辆、绿色双层路线带、App BMD 建筑／道路与立交层级。路线及拥堵段按 App 道路层级抬升，避免经过高架时仍画在地面。进入 3D 后可在图层菜单切换日夜样式；地面、道路和建筑选用 BMD 对应配色。当前中心瓦片的 LNDS 真实车道边界在底图之后异步加载，失败时不影响导航。

3D 路线带现按当前路线里程裁到**正在行驶的网格小段内部**，而不只丢弃整个已驶过的小段。拥堵带使用同一裁剪逻辑；GPS 纠偏导致进度回退时，原始网格顶点会恢复后再裁剪，避免路线带永久缩短。几何回归测试和生产构建已通过，车机画面仍待核对。

当前视野的 3D 地图先请求导航所需的 14 级道路和 15 级建筑，并在两者结束后显示；3／6／8／10／12 级远景地表继续补全。远景层级失败时保留已显示的导航底图。这个顺序减少首幅导航画面的等待，但总下载量是否下降仍需以车机网络面板实测。

固定 APK 的 `MapEngineInitParam.MainMapInitParam()` 明确选择 `mapprofile_1`；先前 TMC 误用 `laneprofile_1` 的 `CONFIG_TYPE_STATE_LANDSCAPE` FOV（17 级为 32°）。主 3D 导航画布现采用 `mapprofile_1` 的 `CONFIG_TYPE_STATE_LANDSCAPE_NAVI`：15 级 36°、16 级 33.006°、17 级 27.006°、18–19 级 42.09°、20–22 级 42°；非整数缩放在相邻表项间插值以保持连续。同表的 `MaxPitchAngle` 在 16、17、18 级分别为 50°、54°、70°；跟车相机此前以较低机位超出此上限，现仅在超限时抬高机位。当前的车辆屏幕锚点仍是 TMC 的布局选择，前视焦点按 FOV 投影反算以避免缩放时跳位。`MaxPitchAngle` 是上限，并非 APK 当前实际俯仰角；镜头距离和实际俯仰仍需与 APK 实机画面对照，不能据此声称 3D 导航已像素级复刻。

2026-10-04 车机画面显示车辆过小且落在建筑旁：TMC 跟车距离缩短，镜头降低，并随导航缩放调整前视焦点，让车辆接近 2D 导航的下方锚点。导航位置只有在精度有效时才更新画面，匹配路线的点投影到路线；低精度定位保留上一可信车位，首次无可信位置时暂不画车。建筑前景遮挡改为仅对实际显示的车辆清理视线，移除会产生噪点光环的随机透明裁切。APK 的横屏 FOV 和地图姿态配置已核对；跟车距离与实际俯仰由 TMC 调整，仍需实车视角对照。

3D 画布现在可手动操作相机：鼠标左键或单指平移，鼠标右键或双指旋转，滚轮／双指及右侧按钮缩放。手动操作会暂停自动跟随；当前视角按钮可重新跟随车辆。平移超出局部原点后会重设地理原点并加载相邻地图，同时保持相机地理位置，切回 2D 时同步已浏览的地图中心。此交互已通过相机几何测试和生产构建，车机触屏手势仍需实测。

2026-10-04：短横屏的 3D 跟车镜头原来只离车辆约 70 米，110 米后的转弯会被裁出画面。APK 的 `TripNaviMapUtil.setNaviProjCenterPadding` 会通过 `DriveProjenterCenterPadding` 按导航控件占用区域调整投影中心；`mapprofile_1` 只给出视场角和最大俯仰角，不能直接推出相机离车距离。TMC 现将 17 级跟车距离调到约 160 米，并把车辆屏幕锚点放到约 75% 高度，随速度平缓拉远。短横屏模拟路线实测 180 米前方弯道可见，且地图仍填满画布；继续拉到约 200 米时会露出当前 600 米地图块边界，因此没有采用。这个距离是 TMC 针对现有地图块的画面校准，不是已确认的 APK 原生常量。

2026-10-04：3D 转弯时车模与相机原来共用完全相同的航向，车身在屏幕上恒定朝上，看不出转动。现在车身按已平滑的路线／GPS 航向实时旋转，相机以约 450 ms 半衰期沿最短角度追随；转弯期间车辆会相对道路和镜头可见地转向，转完后恢复车头向上。手动拖动视角时不再自动追随，恢复跟随时重新对齐。此处是 TMC 对原生导航跟车观感的实现，不是已提取的 APK 相机动画常量。

LNDS 车道边界现在随首幅道路与建筑画面启动加载，无需等待全部远景地表请求结束。真实 APK 瓦片离线交叉核对还覆盖了 14 级道路、地表、公交点，15 级建筑以及 3 级省市标注：浏览器 BMD 解码与 Python 解码的要素数量、抽样几何和中文标注一致。该核对证明两端格式实现一致，不能代替车机上的完整加载与视觉验收。

行驶中每约 120 米切换底图时，旧瓦片保留至新瓦片完成，避免整屏闪空；车辆在慢请求期间驶出当前范围时，先让在途瓦片完成并入缓存，再按最新位置加载，避免高速行驶中反复取消请求。这里复用的是 APK 数据与资产，浏览器用 Three.js 重绘，并未运行 APK 的原生地图渲染器；LNDS 线目前没有原生虚实线、颜色和高程语义。特色地标已按 App 模型索引按需加载原始 GLB/KTX2，旋转方向和实车光照仍需对照。

车机浏览器现将已解码的道路／建筑和 LNDS 瓦片写入 IndexedDB，2D 与 3D 先读取本机缓存，再向后端请求缺失瓦片；完整的 3D 建筑瓦片也可供 2D 使用。数据使用浏览器支持时的 gzip 压缩；缓存有效期默认 7 天、总量上限默认 96 MiB、单瓦片上限 12 MiB，并按最近使用时间淘汰。设置页可修改本机缓存时间和容量，也可查看与清空；IndexedDB 不可用时仍走现有服务器缓存。建筑保留 BMD 的轮廓、分段高度和导航专用日夜样式的五槽颜色及 APK 原版立面图片；圆形轮廓平滑处理。APK 的 `BUILDING_WINDOW` 着色器按高度混合底部色与顶部色，前端现复现这一步，不再把五槽误当作不同朝向的墙面。立面贴图的 UV 比例、楼层重复和其他颜色槽绑定仍是近似，详见 `docs/tesla-building-layer.md`。地标异步加载或切页后会释放几何、材质和贴图，避免大模型资源滞留。已核验的 LNDS FlatBuffer 边界表只有几何及未解释的数值，没有足以可靠区分虚实线、黄白线的样式字段，故继续使用中性色，不凭几何猜测交通标线语义。

2D／3D 基础道路、地表以及 3D 的 15 级建筑现传输原始 BMD 内容，由浏览器 Worker 解码；服务端仅拆开源响应外层并附上已核验的样式表。前后端协商 `application/vnd.tmc.amap-bmd` 二进制批次，避免先把 BMD 转为 Base64 JSON 再在浏览器还原；旧客户端仍可读取 JSON 响应。解码后的瓦片继续共用 IndexedDB 缓存，Worker 不可用、构造失败或启动后未就绪时，保留原始缓冲区并改由主线程解码 BMD；BMD 格式损坏或连续两次解码 Worker 故障时回退至原完整 JSON 接口；临时 429、502、网络超时和单次 Worker 故障保留 BMD 路径，避免后续持续下载大 JSON。两块真实样本核对：14 级道路瓦片 gzip 由完整 JSON 的约 107 KiB 降到二进制批次的约 35 KiB，15 级建筑瓦片由约 38 KiB 降到约 14 KiB，前端解码结果与 Python DTO 的道路层高／样式和 202 栋建筑部件一致。数据量只代表样本瓦片，不等于完整导航会话的流量。TMC 会话过期时地图请求停止重试，页面弹出 TMC 密码框，登录后恢复地图；这不是高德账号登录。

浏览器交给 BMD Worker 的同批瓦片共用一块二进制响应缓冲区；现在只转移一次，不再为 Worker 复制整批地图数据。真实 14 级道路样本经过后端批次封包和前端解析后，解出 1323 条道路、112 块地表和 26 个公交点，与本机基准一致；车机端耗时仍需实测。

地图与车道的短生命周期 helper 现各自复用同源 APK 版本清单 120 秒；清单仅保存白名单下载主机及瓦片版本，过期或不合法即重新请求，设置页“清空缓存”也会删除。LNDS 每块瓦片仍独立进行原生解码；本机实测同一 LNDS 清单首次查询约 1.6 秒、立即复用为不足 1 毫秒，这只是版本发现耗时，不代表整块瓦片或车机首屏耗时。

导航车道提示另取自 App `routeguide` 的 NCP `lanenew` 事件，与 LNDS 底图车道边界、路口放大图均为不同数据。服务端校验事件的路线身份、剩余里程、车道数、箭头编码与时间段后映射到解码路线里程；浏览器接近事件位置时，在转向卡片与路口图之间显示 APK 的原版车道箭头 SVG。模拟导航与真实导航共用这套路线事件。样本响应的 30 个车道事件及其用到的箭头资源均已离线核对；`optimalLane` 的动态推荐动画不在已验证的 NCP 字段里，因此没有推断或伪造具体推荐车道。

2D 道路现同样读取 BMD `paintKey` 对应的日夜颜色、透明度和内外描边宽度，先绘制全部道路外描边，再绘制内描边；旧缓存缺少样式时仍使用原有单线回退。样式单位沿用 3D 地面的 0.1 比例，尚需车机画面对照确认最终视觉比例。
